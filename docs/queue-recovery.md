# 上传队列恢复

当前部署为单 API 进程。任务记录保存于 MySQL，Redis 负责执行调度。

- 每分钟检查一次超过两分钟未更新的任务；Redis 查询失败时不修改任务。
- 新任务使用任务 ID 作为唯一队列 ID，并完整保存批次、网盘账号及频道账号选择。
- 自动恢复仅面向从未开始执行、没有 AI/网盘/上架痕迹且本地原文件存在的上传任务。恢复后仍遵守空闲窗口；全部有手动标题的任务不等待 AI 时段。
- 旧版批量任务缺少账号信息、缺失资源或已有处理痕迹时，标记失败并解释原因，需人工核对后重新处理。
- 重启前中断的运行任务不会自动重放，避免重复发帖；历史自动发帖也会标记中断。当前进程仍在运行的长任务不会按固定时长误判失败。
- 执行前重新检查空闲时段；已经开始的任务不在窗口结束时强制中断。修改窗口不会立即提前已有延迟任务，但执行时会使用最新设置。
- 数据库原子认领阻止同一任务重复执行；不承诺不同任务提交相同资源、或外部平台请求成功但响应丢失时的全局 exactly-once。

## Redis 运维

队列恢复不能代替 Redis 安全配置。上线诊断会提示队列记录不一致，以及全网卡监听且保护模式关闭的风险。

若 Redis 被其他项目共用，不要直接清库或修改全局 ACL/监听地址。先盘点调用方，再选择隔离实例或为各应用设置独立账号及权限，禁止业务账号执行 FLUSHALL/FLUSHDB，限制 6379 的网络访问。单独选择 Redis 数据库编号不能抵御 FLUSHALL。

建议为队列实例启用持久化并备份，禁止内存淘汰队列数据。持久化本身不能阻止合法命令执行清库。

本地回归：`npx tsx --tsconfig apps/api/tsconfig.json --test apps/api/src/modules/admin/queue-recovery.test.ts`。测试只使用模拟队列与数据库，不上传、不发帖。
